## 6. What looks wrong to me

Ranked by how much damage it could do. **The first two are blocking in my
view — I would not run `--submit` until they are resolved.**

### 6.1 BLOCKING — an empty plan does not suppress trading; it silently hands control to the mechanical scanner

`tools/paper_session.py`:

```python
proposals = propose_from_plan(today) or propose_mechanical(adapter, symbols)
```

An empty plan is `[]`, which is **falsy**, so `or` discards it and runs the
20-day-breakout scanner instead. Verified empirically this session, read-only,
with the real plan file on disk:

```
1) plan file on disk : []
2) propose_from_plan  : []
3) propose_mechanical invoked despite a written plan? -> True
4) proposals the runner would gate -> ['FAKE']
```

The consequence is precise and serious: **the runbook's instruction to "have
trade-plan write `state/plans/<today>.json` so a later submit would evaluate
the identical plan" does not hold for an empty plan.** A later
`--submit` would evaluate *the mechanical scanner's output at that moment*,
not the empty plan I deliberately wrote.

Today this is harmless only by luck — the mechanical scan also finds nothing,
because nothing is above its 20-day high. On any day where the agent decides
`NO_TRADE` for a reason the scanner cannot see (an FOMC, a halt, an
unreadable regime) and writes `[]` to say so, the runner would substitute
breakout proposals and could submit them. **A deliberate refusal to trade is
indistinguishable, to this code, from having no opinion.**

Suggested fix, for a human to make with a test: distinguish "no plan file"
from "a plan file that is empty" — fall back to mechanical only when the file
is absent, and treat a present-but-empty plan as a binding instruction to
trade nothing.

I did **not** apply this fix. The point of a rehearsal is to exercise the
system as it actually is, and a human reads this before anything is
submitted. Flagging rather than patching is also the honest move given that
patching it would have changed the very output I am reporting.

### 6.2 BLOCKING — `NO_TRADE` posture has no enforcement in code anywhere

`grep -rn -i "posture|briefs|NO_TRADE" tools/ engine/ adapters/ tests/`
returns exactly one hit, and it is a comment string in
`engine/model_policy.py:68`. Nothing in the runner reads the brief, the
posture, or even checks that a brief exists for today.

So the brief's `Posture` field — which the skill calls "binding", and which
`RISK_OFF` and `NO_TRADE` are supposed to act through — is prose enforced
only by the model's own compliance. `CLAUDE.md`'s one rule that outranks
everything is *"The model decides what to trade. Code decides whether it is
allowed."* Posture is currently on the wrong side of that line.

Combined with 6.1: today the *only* thing standing between a `NO_TRADE` brief
and a live order under `--submit` was that the breakout scanner happened to
return empty. That is a coincidence, not a control.

### 6.3 Dry-run fills would pollute the measured track record

`paper_session.main()` calls `state.append_fill(...)` on **every** approved
proposal, including under `--dry-run`, tagging it `dry_run: True`. But
`tools/review.closed_trades()` has no `dry_run` filter. Verified read-only:

```
dry-run-only fills produce 1 closed trade(s):
  [{'symbol':'XYZ', 'pnl':20.0, 'R':2.0, ...}]
```

Two consequences:
1. Previewed tickets count toward `option_min_closed_trades` (30) and toward
   measured expectancy — the two gates that unlock the option sleeve, and the
   Phase 2 exit criterion. A sufficiently rehearsed agent could unlock
   options on trades that never happened.
2. Worse, `closed_trades()` pairs FIFO on `lots[0]`. A phantom dry-run *entry*
   left in `fills.jsonl` would pair against the next **real** sell of that
   symbol, corrupting that real trade's entry price and its R.

**This did not bite today** — nothing was approved, so nothing was appended,
and `state/fills.jsonl` still does not exist. It bites on the first rehearsal
that approves anything, which is every future rehearsal that finds a setup.
