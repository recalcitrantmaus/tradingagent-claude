## M-26 — `CLAUDE_CODE_SESSION_ATTENDED` does not measure attendance. M-22's fix does not bind. *(NEW, high)*

**This session is unattended, and `is_attended()` returns `True` in it.**

```
$ env | grep ATTENDED
CLAUDE_CODE_SESSION_ATTENDED=1
$ python3 -c "from engine.model_policy import is_attended; print(is_attended())"
True
```

M-22 was adopted overnight precisely so an unattended session cannot clear a
blocking gate with `--model`. `is_attended()` reads one environment variable
and fails closed on absence, which is the right shape — but the variable is
**set at the environment level**, so it is the same constant for every session
launched there, exactly like `TRADING_AGENT_MODEL`. It answers a per-session
question with an environment-wide value, and it fails in the **permissive**
direction.

This is the third instance of one pattern: M-17 (effort), the model finding
before it, and now attendance. Every input to the binding routing control is
an operator declaration, and every one of them over-claims.

Concretely: the Tuesday session prompt states *"this session is unattended, so
that gate will refuse you, and that is correct."* **It would not refuse.** A
blocking task run here with `--model claude-opus-5` clears the attendance
check today; only the effort floor (`high` < `xhigh`, M-27) happens to stop it,
and that is luck, not design.

**Not fixed here, deliberately.** `engine/model_policy.py` is in the `ask` tier
of `.claude/settings.json`, the fix needs a test per CLAUDE.md, and an
unattended session tightening the very control that decides whether it is
trusted is the wrong hand on that lever. I ran no blocking task and did not
reach for `--model`; the discipline M-22 names held on judgement, which is the
situation M-22 exists to stop relying on.

**To decide at the review:**
- whether the harness exports any per-session attendance signal at all — if it
  does not, `is_attended()` cannot be made honest from inside the session, and
  the correct fix is to unset `CLAUDE_CODE_SESSION_ATTENDED` in the
  environment so the gate fails closed everywhere and an attended session
  passes it *per invocation* (e.g. `--attended` alongside `--model`, both
  asserted by the human, in one place)
- whether `TRADING_AGENT_MODEL` and `CLAUDE_CODE_SESSION_ATTENDED` should be
  removed from the environment entirely, given both are now known to answer
  per-session questions with environment constants

## M-27 — `preflight_phase2` prints the declared effort, not the measured one. *(NEW, medium)*

M-17's fix landed in `engine/model_policy.py` and did not reach the first
thing every session reads. `tools/preflight_phase2.py:114`:

```python
e = os.environ.get("TRADING_AGENT_EFFORT")
```

So this morning's preflight printed `[ok] model routing  effort xhigh` while
the harness reported `CLAUDE_EFFORT=high` and the session ran at **high**.
`model_check` gets it right on the same inputs —

```
ok: EFFORT MISMATCH: harness reports 'high', TRADING_AGENT_EFFORT declares
    'xhigh'. Using the harness value; fix the declaration.
ok: 'execution' requires effort >= xhigh; running high
ok: non-blocking: proceed, and record the downgrade in the journal.
```

— so the two tools disagree about the same session, and the one that speaks
first and loudest is the wrong one. Narrow fix: read `effort_and_source()` and
print the provenance, exactly as the model half of that same function already
does.

**Recorded, not fixed** — `preflight_phase2` is the gate this firing had to
clear, and editing a gate in the run it is gating is the shape of thing this
project exists to refuse. It changes no trade today: the routing table makes
every task this session runs warn-and-continue, and the downgrade to `high` is
noted here as that table requires.

## M-28 — the model-gate tests were deciding on the ambient environment. *(NEW, medium — FIXED here)*

**`preflight_phase2` exited 1 at 09:36 on a red suite**, one failure:

```
FAIL: test_an_explicit_model_clears_a_blocking_task
  tests/test_model_policy.py:63  AssertionError: False is not true
```

No code changed between the overnight commit that ran it green and this
morning's red. The cause: `env()` in that file patches with `clear=False`, so
any variable a test does not pin falls through to the real environment. That
test pins `TRADING_AGENT_EFFORT` and not `CLAUDE_EFFORT` — and M-17's fix made
`CLAUDE_EFFORT` the value that decides. Overnight it was `xhigh` and the test
passed; at 09:35 it is `high`, below the `weekly-review` floor, and the same
assertion fails. **A test about the environment was being decided by the
environment**, which makes it evidence about the machine and not about the
gate.

Fixed by pinning `CLAUDE_EFFORT` and `CLAUDE_CODE_SESSION_ATTENDED` in the two
tests of `TestBlockingTasksRefuseAnUnverifiedModel` that exercise the *model*
half, so each asserts the thing it names. **No production code was touched and
no gate was weakened** — `is_attended()`, `effort_and_source()` and `check()`
are byte-identical. Verified under three ambient environments:

```
CLAUDE_EFFORT=high  ATTENDED=1        166 tests OK
CLAUDE_EFFORT unset ATTENDED unset    166 tests OK
CLAUDE_EFFORT=low   ATTENDED=0        166 tests OK
```

`preflight_phase2` then exited 0 and the smoke test ran after that, not before.

**To decide at the review:** whether `env()` should default to `clear=True`.
The other suites use it too, and this failure mode is silent — it does not
make a test fail, it makes a test *stop measuring* and then fail later on an
unrelated machine. Second-order but worth one pass.
