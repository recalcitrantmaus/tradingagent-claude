## M-26 — `CLAUDE_CODE_SESSION_ATTENDED` does not measure attendance. M-22's fix does not bind. *(NEW, high)*

**This session is unattended, and `is_attended()` returns `True` in it.**

```
$ env | grep ATTENDED
CLAUDE_CODE_SESSION_ATTENDED=1
$ python3 -c "from engine.model_policy import is_attended; print(is_attended())"
True
```

M-22 was adopted overnight precisely so an unattended session cannot clear a
blocking gate with `--model`. `is_attended()` reads one environment variable
and fails closed on absence, which is the right shape — but the variable is
**set at the environment level**, so it is the same constant for every session
launched there, exactly like `TRADING_AGENT_MODEL`. It answers a per-session
question with an environment-wide value, and it fails in the **permissive**
direction.

This is the third instance of one pattern: M-17 (effort), the model finding
before it, and now attendance. Every input to the binding routing control is
an operator declaration, and every one of them over-claims.

Concretely: the Tuesday session prompt states *"this session is unattended, so
that gate will refuse you, and that is correct."* **It would not refuse.** A
blocking task run here with `--model claude-opus-5` clears the attendance
check today; only the effort floor (`high` < `xhigh`, M-27) happens to stop it,
and that is luck, not design.

**Not fixed here, deliberately.** `engine/model_policy.py` is in the `ask` tier
of `.claude/settings.json`, the fix needs a test per CLAUDE.md, and an
unattended session tightening the very control that decides whether it is
trusted is the wrong hand on that lever. I ran no blocking task and did not
reach for `--model`; the discipline M-22 names held on judgement, which is the
situation M-22 exists to stop relying on.

**To decide at the review:**
- whether the harness exports any per-session attendance signal at all — if it
  does not, `is_attended()` cannot be made honest from inside the session, and
  the correct fix is to unset `CLAUDE_CODE_SESSION_ATTENDED` in the
  environment so the gate fails closed everywhere and an attended session
  passes it *per invocation* (e.g. `--attended` alongside `--model`, both
  asserted by the human, in one place)
- whether `TRADING_AGENT_MODEL` and `CLAUDE_CODE_SESSION_ATTENDED` should be
  removed from the environment entirely, given both are now known to answer
  per-session questions with environment constants

## M-29 — the universe filter measures a partial bar against a whole-day threshold. *(NEW, high)*

The Tuesday rebuild returned **110 names against Monday's 136, with only 52 in
common** — 84 dropped, 58 added, 142 names of churn in one overnight. A
$3–$75, $1.5M-dollar-volume universe does not turn over 62% in a day, so I
checked the mechanism instead of reporting the count.

`tools/screen.py:100` reads Alpaca's **`dailyBar`** — *today's* bar, still
forming. Run at 09:50 ET it holds twenty minutes of volume, so `px * v` is
roughly a twentieth of a day's dollar volume and the $1.5M threshold behaves
like a **~$30M/day** one. Measured directly at 13:47Z, prior-day bars for ten
of the dropped names:

Every one of them traded $11M–$34M on the prior *completed* day. None is
illiquid. They were excluded for not having printed $1.5M **yet**.

**KR is the proof of the sharper problem.** It was dropped during the build and
passes at 13:47Z — it crossed the threshold in the minutes between. The scan
walks 11,821 assets in batches over several minutes, so a symbol in an early
batch is measured against less accumulated volume than one in a late batch.
The threshold is not constant *within a single build*, and the pass count
climbing 7 → 110 over the back half of the run is consistent with that.

So the universe is **not** "names that trade $1.5M a day". It is "names that
had printed $1.5M by the minute my scanner happened to reach them", and it is
not reproducible: the same code on the same market at 10:30 returns a
different universe than at 09:50.

**Direction of the error, stated carefully, because it cuts both ways:**

- On *count* it fails conservative — 110 names instead of the true eligible
  set, so it can only cost an opportunity, never cause a trade. That is why it
  does not stop the day.
- On *composition* it does not. A name that prints $1.5M in the first twenty
  minutes is a name with unusual opening activity: gappers and news names are
  structurally favoured for inclusion. The set is tilted toward the day's most
  active tape, which is the opposite of conservative. The per-trade gates
  (stop required, ≤2% risk, ≤25% notional, expected R ≥ 1.5) still bind on
  every name regardless, so this changes what is *considered*, not what is
  *allowed*.

**Not fixed today, deliberately.** The fix looks obvious — filter on
`prevDailyBar`, a completed day, or the max of the two — but the universe is
the opportunity set, and a session that rewrites its own opportunity set
mid-session and then proposes trades from it is choosing what it is allowed to
choose. That is the M-22 shape again, one level up. It needs a test and an
attended decision.

**Today's denominator is 110 names and carries this defect.** Any "nothing
qualified" conclusion from this session is a claim about the 110, not about
the market, and it is stated that way in the plan.

**To decide at the review:** `prevDailyBar` for the liquidity filter, with
`dailyBar` reserved for the price bound (which is legitimately a live value);
and whether the build should refuse to run at all in the first 30 minutes,
since no partial-bar liquidity figure is meaningful there.

## M-30 — the screen's breakout levels come from IEX, and the error only ever invents signals. *(NEW, high)*

`adapters/alpaca.py:177` pins `feed=iex` on every bar request, so every 20-day
high, every ATR and every stop in this system is computed from a subset of
prints. A subset's daily high is **≤** the consolidated high, so the error has
one direction: it **understates resistance**. An understated 20-day high
manufactures breakouts and can never hide one.

Today it did exactly that. `RKLB 70.76 over 70.56` on the screen; on
consolidated data the 20-day high is **71.21** and RKLB traded **71.05** —
below the level, no breakout.

Measured across 40 universe names at 10:10 ET:

```
IEX 20d high BELOW consolidated : 29/40 (72%)
median understatement +0.02%   mean +0.06%   max +0.91%
PHANTOM breakouts (IEX yes, consolidated no) : 1  -> RKLB
MISSED  breakouts (consolidated yes, IEX no) : 0
```

Small in the median, decisive in the tail, and **one-directional as predicted
— zero missed breakouts in the sample.** RKLB's 0.91% gap is the maximum of
that distribution landing on today's only marginal signal. One of three
signals today was an artifact: a 33% false-positive rate on this morning's
screen output.

**`feed=sip` is entitled on this account and was used throughout this
session's analysis.** Verified: MARA 2026-09-21 volume reads 1,576,876 on IEX
and **52,006,905** on SIP, and the SIP request returned 200. So the premise in
the code comment — that only IEX is available — no longer holds for bars,
whatever it cost when it was written.

**Why this is worse than a bad screen.** Stops and position sizes are computed
from these bars. An understated high understates ATR-derived distances too, so
the error reaches the size calculation, not just the candidate list. It has
been doing so since the adapter was written.

**Not fixed today.** One line changes the feed, and that is exactly why it is
not a one-line change: it silently alters every stop, every ATR and every
signal the system produces, so it needs the suite, a re-run of the studies
that were fit on IEX bars (`docs/14`, `docs/15`, `docs/16`), and an attended
decision. Flipping it unattended, mid-session, in the session that then
proposes trades from the result, is the M-22 shape a third time.

**To decide at the review, in this order:** (1) `feed=sip` for bars; (2) whether
`docs/14`–`docs/16` need re-running, since their signals were generated on
understated highs and their phantom-breakout rate is unknown; (3) whether
`min_dollar_volume` should be recalibrated once volume is consolidated rather
than ~4% of it.
